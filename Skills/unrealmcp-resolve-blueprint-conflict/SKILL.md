# Resolve Blueprint conflicts in chat

1. Verify the exact attached project and live tool schemas. Run `ListBlueprintGitConflicts` and record the exact paths and stage revision from `CompareBlueprintMergeStructure`. Use `graphGuid` for the graph under review and `focusNodeGuid` for exact incident execution and data links. Page the relevant evidence using `nextCursor`. Use `InspectBlueprintCommit` for earlier logic. Call out unreadable stages and truncated views before drawing conclusions.
2. Show a small, labeled graph in chat with Base, Ours, Theirs, and the current working result when it differs. Use named pins and distinguish execution from data. Show shared dependencies, additions, removals, and unverified behavior. Keep GUIDs in the patch and expose them when a label is ambiguous. For large graphs, show the affected route rather than the entire graph.
3. Ask the human to choose the desired behavior for the exact asset and graph. Offer only evidence-backed choices, explain what each preserves or changes, and allow custom behavior or more evidence. Treat a choice to see a preview as approval to prepare the preview. Ask separately before applying, saving, staging, or replacing a whole asset.
4. Bind the chosen change to the recorded `stageRevision` and the live graph revision. Author an explicit patch with stable node IDs and exact pin endpoints. Use `PreviewBlueprintSideReplay` when useful for compatible existing-node edits. Run `ApplyBlueprintGraphPatch` or `WriteBlueprintGraphDsl` with dry run enabled and saving disabled. Show additions, deletions, disconnected pins, connections, and any unsupported operations. A blocked preview is not approval to work around it by dropping logic.
5. On explicit apply approval, recheck the stages and working revision. If either changed, show new evidence and preview again. Apply the same reviewed edits with compilation enabled and saving disabled, unless the human explicitly defers compilation. If a change requires a sequence of tools, show the transaction boundaries in the preview. For independently approved saved checkpoints use `ApplyBlueprintMergePlan` and keep the same UUID, payload, and preview token. On timeout, inspect the original operation ID and verify the live graph before retrying.
6. Show the resulting graph slice and compile receipt in chat. Ask separately to save, then if requested preview `ApplyBlueprintConflictStage` and apply its exact token only after explicit staging approval. Report the save and index results. Commit or push only when explicitly requested.
